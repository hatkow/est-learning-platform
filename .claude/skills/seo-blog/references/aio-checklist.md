# AIOレビュー観点（人が見るところ）

`node scripts/lint-blog-draft.mjs` は形式を検査するが、**中身の質は検査できない**。
下書きをレビューする人（および公開ボタンを押す人）が見る観点をまとめる。

## 1. リードは「答え」になっているか

チェッカーは字数しか見ない。100字以内でも、それが**問いへの答えになっていなければ意味がない**。

- 記事タイトルを疑問文に読み替えたとき、リードだけでその答えになっているか
- リードを単独で誰かに見せて、「で、結局どうなの？」と聞き返されないか

## 2. パッセージが単体で成立しているか

各セクションの第一段落を**バラバラに切り出して並べてみる**。それぞれが独立した回答として読めるか。

- 主語が省略されていないか（「〜が必要です」→ 何が？）
- 前のセクションを読んでいる前提の言い回しになっていないか
- 固有名詞が代名詞に置き換わっていないか（「このツール」→「Power Automate」）

## 3. 数値の出所が確認されているか（最重要）

**架空の数字を書かないこと。** これは品質の問題ではなく事実性の問題。

- 数値が入っている場合、その出所を必ず著者に確認する
- 自社の研修実績なら「実際にその数字か」、公的統計なら「出典と時点が本文に書かれているか」
- 出所を確認できない数値は、記事から削るか、一般化した表現に変える

## 4. FAQが周辺の疑問を拾えているか

- 本文の要約の繰り返しになっていないか
- 実際に研修・商談で聞かれる質問が入っているか（営業・カスタマーサクセスに聞くのが最短）
- 質問文が、読者が実際に検索しそうな言い回しになっているか

## 5. AIが既に答えられる内容になっていないか

[docs/blog-style-guide.md](../../../../docs/blog-style-guide.md)「テーマ選定方針」と対で見る。

- この記事の中身は、AIが学習データだけで書けてしまう一般論ではないか
- 自社の研修現場・コンサル経験から来ている一次情報がどこかに入っているか
- 入っていない場合、それはAIOで戦う以前にテーマ選定の問題

## 6. 監修者

- `author` に指定した人物が `lib/authors.ts` に登録されているか
- **本人の掲載許諾を得ているか**（実在の人物を無断で監修者として掲載しない）
- 経歴・保有資格は事実か（盛らない）

## 7. 公開後（月次）

- 狙ったクエリでAI回答に引用されているか（AI Overviews / ChatGPT / Perplexity で実際に検索する）
- GA4でAI検索経由の参照元（`chatgpt.com` / `perplexity.ai` / `gemini.google.com`）が増えているか
- 3か月以上更新のない記事はリライト候補

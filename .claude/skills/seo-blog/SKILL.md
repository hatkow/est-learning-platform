# SEOコラム記事執筆エージェント

毎月、マーブル担当者が手動でこのSkillを実行し、コラム（`/blog`）の記事を作成する。**このSkillは記事を「下書き」までしか作らない。公開は人（レビュー担当者）が記事を読んで承認したときだけ行われる**（下記「承認して公開する」参照）。

作業前に必ず [docs/blog-style-guide.md](../../../docs/blog-style-guide.md) を読み、文体・構成・CTA・**AIO**のルールに従うこと。記事の骨格は [references/aio-article-template.md](references/aio-article-template.md) に置いてある。

## この記事は何を狙うのか（AIO）

2026年現在、検索の主戦場はAI回答エンジン（Google AI Overviews / ChatGPT検索 / Perplexity）に移っている。順位を取ってもクリックされないため、**記事のゴールは「検索1位」ではなく「AIの回答の根拠として引用されること」**。

そのために本Skillが守る要件は4つ。詳細は[docs/blog-style-guide.md](../../../docs/blog-style-guide.md)の「AIO（AI回答エンジン対策）」章。

1. **パッセージ最適化** — AIはページ単位ではなく一節単位で抜き出す。リード100字以内の直接回答、1見出し1質問、各セクション冒頭に50〜140字の結論、指示語で始めない
2. **構造化データ** — 「よくある質問」セクションを3〜5問置くと、サイト側が`FAQPage`を自動生成する
3. **E-E-A-T** — 監修者の経歴・保有資格（`lib/authors.ts`）
4. **情報鮮度** — 「2026年8月時点」のような時点表記

## 前提（契約上のノルマ）

月次で「構成案2本作成・記事3本入稿」。うち1本はクライアント側が自分で執筆・入稿するため、**このSkillが実際に作るのは構成案2本＋本文2本**。

## 実行の流れ

このSkillは1回の実行で「構成案づくり」か「本文執筆」のどちらか1本を対話的に進める。月に必要な本数だけ繰り返し実行する。

### ステップ0. モード確認

**引数でテーマが渡されている場合（例: `/seo-blog Power Automateの承認フロー`）は、確認せずワンショットモードで走る。** 下記「ワンショットモード」を参照。

引数が無い場合は、ユーザーに「今回は①キーワード提案から構成案まで作るか、②すでにある構成案から本文を書いて下書き保存するか、③テーマを渡すので下書き登録まで一気に進めるか」を聞く。

### ステップ1. テーマ確認とキーワード提案

- ユーザーから今回の大枠テーマ（例:「Power Automateの承認フロー」）を受け取る。**テーマそのものはこのSkillが決めない**（クライアント／マーブルが決める前提）。
- 既存記事のカテゴリ・テーマと重複しないか確認する（microCMSの`blog` API一覧、または`content/blog/*.md`のfrontmatterを参照。可能なら`MICROCMS_SERVICE_DOMAIN`/`MICROCMS_API_KEY`が設定されていれば`GET https://{domain}.microcms.io/api/v1/blog?fields=title,slug,category,tags&limit=100`で既存記事一覧を取得し、テーマ被りを避ける）
- テーマに対して、検索されそうな関連キーワード・ロングテールキーワードを5〜8個程度提案する（例: 「Power Automate 承認フロー」なら「Power Automate 承認 作り方」「Power Automate 稟議 自動化」等）。あわせて、[docs/blog-style-guide.md](../../../docs/blog-style-guide.md)の「記事のゴール」に沿い、コース領域（Power Apps/Power Automate/Power BI/Copilot(AI)）との関連度が高いものを優先して提案する。
- **候補キーワードで実際に`WebSearch`を実行し、AI回答の現状を確認する**（記憶だけでキーワードを提案しない）。見るのは次の3点：
  - AIは今このクエリにどう答えているか（すでに答えきっているなら、その角度では引用されない）
  - どのサイトが引用元になっているか（競合が誰か）
  - **何が答えられていないか**（＝こちらが一次情報で埋められる隙間。ここが狙う角度になる）
- 調査結果をユーザーに提示し、狙うキーワードと「AIがまだ答えられていない角度」を1つ（または少数）選んでもらう。

### ステップ2. 構成案モード（①を選んだ場合）

- 確定したキーワードをもとに、[references/aio-article-template.md](references/aio-article-template.md)の骨格に沿って以下をMarkdownでチャットに提示する（**microCMSには書き込まない**）：
  - タイトル案（1〜2案）
  - meta description案（80〜120字）
  - **リード案（100字以内の直接回答）** — AIが最優先で抜き出す位置なので、構成案の段階で確定させる
  - 見出し構成（H2の「本記事で解決できるお悩み」＋H3セクション7〜10本）。各H3には**「そのセクションが答える質問」と「50〜140字の回答パッセージ案」**を併記する
  - **よくある質問の設問3〜5問**（`FAQPage`構造化データの元になるため、ここで確定させる）
  - 記事に入れる**一次情報・数値の当て**（自社の研修現場の実データか、公的統計か）。当てが無いならこの段階でユーザーに相談する
  - 想定文字数
  - 想定カテゴリ・タグ
- ユーザーのフィードバックを受けて調整し、承認されたらここで完了（本文執筆は別セッション・別実行でよい）。

### ステップ3. 執筆モード（②を選んだ場合）

- 承認済みの構成案（このSkillの直前の出力、またはユーザーが貼り付けたもの）をもとに、[docs/blog-style-guide.md](../../../docs/blog-style-guide.md)のトーン・分量・CTAルールに従って本文をMarkdownで執筆する。
  - 本文中に法人向け誘導・CTAを書かない（記事末尾に`BusinessBanner`が自動挿入されるため）
  - 外部リンクは公的・一次ソース（Microsoft公式ドキュメント、`*.go.jp`等）の出典に限る。それ以外は書かない
  - **AIOの規律**（[references/aio-article-template.md](references/aio-article-template.md)の「必ず守る5点」）：リード100字以内の直接回答／各セクション冒頭50〜140字の結論／指示語で始めない／一文100字以内／よくある質問3〜5問／時点表記
  - **数値を書くときは、その出所を必ずユーザーに確認する。架空の数字を実データのように書かない**（実データが無ければ一般化した表現に変えるか、数値に頼らない切り口にする）
  - **自社講座（`/courses/...`）へのリンクは現在書かない**（下記「自社講座への誘導」参照。無効化中なのでチェッカーがエラーにする）
- 完成した本文をユーザーに提示し、レビュー・修正指示を受ける。
- 承認が得られたら、以下の手順で下書きを保存する：
  1. `content/blog/*.md`と同じ形式（YAMLフロントマター＋本文Markdown）で一時ファイルを作成する（例: プロジェクト外の一時ディレクトリ、またはユーザーに確認の上 `content/blog/` 以外の場所。**Gitにコミットしない**ため、`.gitignore`されている場所か、作成後に削除する）
     - フロントマターは最低限 `title` / `slug` / `description` / `category` / `tags` / `author` / `coverColor` / `date` を含める（`docs/blog-style-guide.md`参照）
     - `slug`は英数字・ハイフンで一意なものを作る（既存記事と衝突しないか確認）
  2. **`npm run lint-blog-draft -- <一時ファイルパス>` を実行して品質チェックを通す**（下記「品質チェック」参照）
  3. `npm run publish-blog-draft -- <一時ファイルパス>` を実行する
     - 環境変数（`MICROCMS_SERVICE_DOMAIN`/`MICROCMS_API_KEY`/`MICROCMS_BLOG_ENDPOINT`/`BLOG_REVIEW_NOTIFY_WEBHOOK_URL`）が未設定の場合はエラーで停止するので、`.env.local`の設定をユーザーに確認する
     - スクリプトは登録前に同じ品質チェックを再実行し、「要修正」が残っていれば登録せず停止する
     - スクリプトは常に`status=draft`でmicroCMSに登録する。成功すると編集画面URLが標準出力に表示される
     - `BLOG_REVIEW_NOTIFY_WEBHOOK_URL`が設定されていればレビュー担当者に自動通知される（未設定でもエラーにはならず、ログでスキップが分かるだけ）
  4. 実行結果（下書きの編集画面URL、通知の成否）をユーザーに報告する
  5. 一時ファイルは後片付けする（リポジトリに残さない）

## 品質チェック（保存前に必須）

下書きをmicroCMSへ送る前に、必ず機械チェックを通す。目視レビューだけで済ませないこと。

```
npm run lint-blog-draft -- <記事.md>
```

**`node scripts/...` を直接叩かないこと。** `node`は`.env.local`を自動で読まないため、microCMSの既存記事を見に行けず、slug重複チェックがローカル分だけになる。`npm run`経由なら`--env-file-if-exists=.env.local`が効く。

チェック内容は`docs/blog-style-guide.md`と`CLAUDE.md`のルールをそのまま条文化したもの（実装: [scripts/lib/blog-lint.mjs](../../../scripts/lib/blog-lint.mjs)）。結果は2段階で出る。

**■ 要修正（error）— 直すまで保存しない**

| 検査 | 内容 |
| --- | --- |
| 必須フロントマター | `title` / `slug` / `description` の欠落 |
| slug | 英小文字・数字・ハイフン以外の混入、既存記事との重複 |
| 旧ブランド名 | 「市民開発スクール」の混入 |
| 製品名の表記ゆれ | `PowerApps` / `PowerAutomate` / `PowerBI` 等（正: Power Apps / Power Automate / Power BI）。slugは対象外 |
| 外部リンク | 公的・一次ソース（Microsoft公式・`*.go.jp`等）以外への外部リンク |
| 本文中CTA | 「法人向け研修」「お気軽にご相談」等の法人誘導 |
| 分量 | 本文1,200字未満 |

`npm run publish-blog-draft`も登録直前に同じチェックを再実行し、要修正が残っていればmicroCMSへ送らずに停止する。`--skip-lint`で無効化できるが、**ユーザーから明示的に指示された場合以外は使わない**。

**■ 確認（warning）— 判断して報告する**

一般：分量の目安（2,000〜2,800字）、H3セクション数（7〜10個）、description字数（80〜120字）、tags個数、新規カテゴリの追加、箇条書きの比率、太字の多さ、匿名事例（「A社」等）と数値の併記。

`[AIO]`が付くもの：リード文の字数と前置き、見出し直下の第一段落が50〜140字か、指示語で始まっていないか、よくある質問の有無と設問数・回答字数、100字超の一文、時点表記、単位付きの数値、`author`が「EST編集部」のまま。

警告は自動では直さない。**内容を確認し、直すか・意図的な逸脱として通すかをユーザーに提示して判断を仰ぐ**こと。とくに次の2つは必ずユーザーに確認する：

- 「匿名事例と数値」の警告 → その数字が実案件に基づくものか（架空の事例を実データのように書かない）
- 「単位付きの数値がありません」の警告 → **数字を埋めるために架空の数値を作らないこと。** 実データが無ければ数値に頼らない切り口にする

新規に書いた記事は`[AIO]`警告ゼロを目指してよいが、既存記事はAIO以前の書き方なので警告が多数出る。既存記事について**警告ゼロを目的化しない**（リライトはユーザーの判断）。

引数なしで実行すると`content/blog/*.md`を一括検査する（ルール自体の動作確認用）。

## ワンショットモード

テーマを1つ受け取り、**調査から下書き登録まで人に聞かずに一気に進める**モード。月次のノルマを回す際の標準経路。

```
/seo-blog Power Automateの承認フロー
```

### 手順

1. **事前チェック**（記事を書く前に必ず実行する）

   ```
   npm run preflight-blog-draft -- "<テーマ>"
   ```

   環境変数・既存記事との重複候補・講座誘導の可否・監修者の登録状況をまとめて出す。**終了コードが1なら記事を書き始めない**（microCMSの環境変数が無く、書いても最後に登録できないため）。その場合はユーザーに設定を依頼して停止する。

   重複候補が出た場合は、既存記事と切り口が被らないか自分で判断する。明らかに同じ内容になるなら、書き始める前にユーザーに報告して確認する。

2. **調査**（ステップ1と同じ）— `WebSearch`でAI回答の現状・引用元・answered されていない隙間を調べ、狙う角度を決める。ここはユーザーに選ばせず自分で決めてよいが、**決めた角度と理由は最後の報告に必ず含める**。

3. **構成**（ステップ2と同じ）— チャットには出さず、そのまま執筆に進む。

4. **執筆**（ステップ3と同じ）— [references/aio-article-template.md](references/aio-article-template.md)の骨格とAIOの規律に従う。

5. **品質チェック**

   ```
   npm run lint-blog-draft -- <一時ファイルパス>
   ```

   要修正が出たら直して再実行する。**ただし、内容をでっち上げて警告を消してはいけない**（下記「ワンショットで越えてはいけない線」）。

6. **下書き保管庫に保存**

   ```
   npm run save-blog-draft -- <一時ファイルパス>
   ```

   `data/drafts/<slug>.md` に保存される（`.gitignore`済み・ローカル専用）。**microCMSへのアップはここでは行わない。** アップするかどうかは人がダッシュボードで判断する。

7. **報告**（下記の形式）。作業用の一時ファイルは削除する（保管庫のファイルは残す）。

### ワンショットで越えてはいけない線

対話モードでは人が止められた判断を、ワンショットでは誰も止められない。次の3つは**警告が出たままにして、報告で伝える**こと。勝手に埋めない。

- **`[AIO] 単位付きの具体的な数値がありません`** → **架空の数字を作って埋めない。** ユーザーが一次データを渡していない限り、数値に頼らない切り口で書き、この警告は残したまま報告する
- **`匿名事例（A社等）と数値`** → 実案件の裏付けが無いなら、そもそも事例を書かない
- **`author が EST編集部 のまま`** → 架空の監修者を立てない。`lib/authors.ts`に登録がある場合のみ`author`を変える

一次情報・数値をユーザーが渡してきた場合（「今年の研修受講者は◯◯人」等）は、それを使ってよい。**渡されていないものを推測で書かない。**

### 報告の形式

実行後、次を必ず報告する。

- 狙ったキーワードと、**AIがまだ答えられていないと判断した角度**（判断の根拠も）
- 下書きの編集画面URL、レビュー通知の成否
- **チェッカーで残した警告と、その理由**（とくに数値・監修者まわり）
- レビュー担当者に確認してほしい点（[references/aio-checklist.md](references/aio-checklist.md)の観点）
- 承認して公開する場合のコマンド（下記「承認して公開する」）

**このモードでも、microCMSへのアップも一般公開もしない。** 保管庫への保存までで止まる。その先は人がダッシュボードで確認して進める。

## 自社講座への誘導

**※ 現在は無効。記事に`/courses/...`のリンクを書かないこと。**

講座6件はすべて`lib/data.ts`のサンプルで、レッスン動画も仮のもの。この状態で誘導すると読者を実体のない講座へ送ってしまうため止めてある。チェッカーが`/courses/`リンクをエラーにする。

**有効化されたら**（`scripts/lib/blog-lint.mjs`の`COURSE_PROMOTION_ENABLED`が`true`のとき）、[docs/blog-style-guide.md](../../../docs/blog-style-guide.md)の「自社講座への誘導」に従って書く。要点：

- 記事の文脈に合う講座を、**本文中で1〜2箇所だけ**、柔らかく紹介する（「〜で扱っています」程度）
- **実在する講座にのみリンクする**（存在しない講座slugはチェッカーがエラー。講座名を推測で書かない）
- 露骨な販売・煽り表現（「ぜひご受講ください」「この機会に」等）は使わない。チェッカーがエラーにする
- 法人研修への誘導は引き続き本文に書かない（`BusinessBanner`と重複）

## 下書き保管庫とダッシュボード

生成した記事は `data/drafts/*.md` に溜まる。`.gitignore`済みのローカル専用の置き場で、公開リポジトリにも Vercel にも載らない。

```
npm run blog-dashboard      # http://127.0.0.1:3200
```

ダッシュボードでできること：

- 下書きの一覧と状態（未アップ / microCMS登録済み / 見送り）
- 品質チェックの結果とAIO指標（本文字数・H3数・FAQ数・リード字数・パッセージ逸脱・時点表記）
- 本文プレビュー
- **microCMSへアップ**（下書き登録）。要修正がある記事はボタンが押せない
- 見送り・削除

**ダッシュボードは意図的にローカル専用にしている。** `app/admin/` には認証が無く、そこに未公開記事を置くと誰でも読める状態になるため。デプロイ版のサイトには載せないこと。

状態は各Markdownのフロントマターに持つ（`reviewStatus` / `microcmsId` / `generatedAt`）。

## 承認して公開する

**このSkillは記事を公開しない。** 下書きの登録までがSkillの仕事で、そこから先は人の承認が要る。

1. Skillが記事を生成し、`data/drafts/`に保存する（microCMSにはまだ送らない）
2. **レビュー担当者がダッシュボードで記事を読んで確認する**（[references/aio-checklist.md](references/aio-checklist.md)の観点。とくに数値の出所）
3. 問題なければ、ダッシュボードの「microCMSへアップ」でmicroCMSに**下書きとして**登録する
4. さらに一般公開してよいと判断したら、承認コマンドを実行する：

```
npm run approve-blog-draft -- <contentId>          # 対象を表示するだけ（公開しない）
npm run approve-blog-draft -- <contentId> --yes    # 公開する
```

`--yes`を付けるまで公開されない。対象コンテンツを確認できない場合も公開せずに止まる。

**エージェントがこの承認コマンドを実行してはいけない。** 承認は人の判断であり、人がコマンドを打つことでその判断を表明する。ユーザーから明示的に「承認して」と指示された場合でも、公開されるURLと記事タイトルを提示して確認を取ってから実行すること。

なお、この承認コマンドはmicroCMSの**マネジメントAPI権限**（コンテンツの公開状態を変更）を持つAPIキーを必要とする。通常のコンテンツAPIキーでは401/403で止まる。

## 公開後の効果測定（月次）

下書きの公開後、翌月の作業時に前月分を確認して報告する。

- 狙ったキーワードで実際に`WebSearch`し、**AI回答に自社記事が引用されているか**を見る。引用されていない場合、AI回答が何を引用しているかと比べて足りない要素（一次情報・数値・構造）を次の記事に反映する
- GA4（導入済み）で、AI検索経由の参照元（`chatgpt.com` / `perplexity.ai` / `gemini.google.com` / `copilot.microsoft.com`）からの流入を確認する
- 公開から3か月以上更新されていない記事はリライト候補として挙げる（情報鮮度はAIの判断材料になる）

レビュー観点の詳細は [references/aio-checklist.md](references/aio-checklist.md)。

## やってはいけないこと

- エージェントの判断でmicroCMSの記事を「公開」状態にすること。`approve-blog-draft.mjs`を人の確認なしに実行すること（公開は人の承認行為）
- 記事本文中に法人向けCTAを入れること。公的・一次ソース以外への外部リンクを張ること
- **数値の警告を埋めるために、架空の数字・事例を作ること**（実データが無ければ数値を使わない切り口にする）
- 実在の人物を、本人の許諾なく`author`／監修者として掲載すること
- 存在しない自社講座へのリンク・講座名を書くこと（推測で講座名を作らない）
- ワンショットモードで、事前チェックが失敗しているのに記事を書き始めること
- エージェントの判断で下書きをmicroCMSへアップすること（アップは人がダッシュボードで行う）
- 下書き保管庫（`data/drafts/`）をGitにコミットすること
- ワンショットモードで、警告を消すために数値・事例・監修者をでっち上げること
- テーマそのものを勝手に決めて執筆を進めること（テーマは必ず人から受け取る）
- 品質チェック（`npm run lint-blog-draft`）を飛ばして下書きを保存すること。`--skip-lint`をユーザーの指示なしに使うこと
- 品質チェックの警告を、ユーザーに見せずに勝手に処理すること（本文の書き換えも、無視も、判断を仰いでから）
- `content/blog/`配下に作業用の一時ファイルをそのまま置き続けること（Git管理下の本流コンテンツと混同するため）

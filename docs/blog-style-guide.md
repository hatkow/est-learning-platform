# コラム記事 執筆スタイルガイド

`/blog`（コラム）に新しい記事を追加する際の執筆ルールです。既存10記事（`content/blog/*.md`、現在はmicroCMSへ移行済み）から抽出した実際のパターンをまとめています。`.claude/skills/seo-blog/`のSkillはこのガイドに沿って構成案・本文を作成します。

## ブランド表記（CLAUDE.mdより）

- サイト名は「**AI・Powerplatformスクール**」で統一（旧名称「市民開発スクール」は使わない）
- 「**Power Apps**」「Power Automate」「Power BI」はスペースあり表記に統一
- 運営会社は「イースト株式会社」

## 記事の構造

### フロントマター（必須項目）

```yaml
title: "記事タイトル — サブタイトルがあれば ～で挟む～"
description: "80〜120字程度。一覧・検索結果・SNSシェア時に表示される要約"
date: 2026-05-19          # YYYY-MM-DD
category: 生成AI活用        # 自由記述。既存例: 生成AI活用 / DX・内製化 など
tags: [キーワード1, キーワード2, キーワード3]  # 3〜5個
author: EST編集部
coverColor: "#1a56a0"       # アイキャッチ未設定時の背景色
coverImage: "/images/blog/xxx.png"  # microCMSでは `eyecatch` フィールド
```

microCMS上の実際のフィールドID（`docs/microcms-setup.md`参照）: `title` / `slug` / `description` / `content`（本文HTML） / `eyecatch` / `category` / `tags` / `author` / `date` / `coverColor`。`slug`は英数字で一意にする（例: `powerapps-approval-flow`）。

> **注意**：`docs/microcms-setup.md`のSTEP3では`category`・`tags`を「複数」と案内しているが、実際にクライアント側で作成された本番の`blog` API では**どちらも単一テキスト型**（配列ではない）。フロントマターでは`tags: [キーワード1, キーワード2]`のように配列で書いてよいが、`scripts/publish-blog-draft.mjs`が送信時にカンマ区切りの1文字列へ自動変換する。

### 見出し構成

- 記事冒頭に「**本記事で解決できるお悩み**」のようなH2（`##`）で、読者の検索意図・悩みを箇条書き2〜4個で明示する（SEO的にも検索意図と本文の一致を示す上で有効。全記事必須ではないが、実務系のハウツー記事では推奨）
- 本文の各セクション見出しはH3（`###`）を基本とする（`## 本記事で解決できるお悩み`のような冒頭ブロックを除く）
- セクション数の目安は7〜10個。最後は「**おわりに**」または「**まとめ**」で締める

### 文体・分量

- です・ます調。断定しすぎず、実務担当者への語りかけるようなトーン
- 1記事あたり **2,000〜2,800字程度**（日本語文字数、コードブロックや見出しを除く本文）
- プローズ（地の文）中心。箇条書きは要点整理のときだけ使い、多用しない
- 比較整理が必要な場合のみ表（Markdownテーブル）を使う
- 太字（`**text**`）で要点を強調するのは1セクションに1〜2箇所程度
- **外部リンクは「公的・一次ソースの出典」に限る**（下記「外部出典の扱い」参照）。それ以外の外部サイトへのリンク・引用は行わない（自社発信の一次コンテンツとして完結させる）

### CTA（重要）

**本文中に法人向け研修への誘導文・CTAリンクを書かないこと。** 記事末尾には`app/(main)/blog/[slug]/page.tsx`が`<BusinessBanner />`を自動挿入しており、「自社の業務に合わせた研修を、お考えですか？」という定型の法人向け誘導が必ず表示される。本文側で重複したCTAを書くと冗長になる。

## 記事のゴール（サイト全体の優先順位）

CLAUDE.mdの通り、このサイトの目的は動画コンテンツ販売ではなく**法人向け研修（コンサルティング）の受注**が最優先。コラム記事は検索流入から興味関心を育て、`BusinessBanner`経由で`/business`（法人向けページ）へ橋渡しする役割を担う。したがって：

- 記事テーマは「読者が自力で完結できるハウツー」よりも、「理解は深まるが、自社導入には専門知識が要る」と感じてもらえる粒度が望ましい
- Power Apps / Power Automate / Power BI / Copilot(AI) など、サイトのコース領域と重なるテーマを優先する（記事→コース→法人相談の導線が成立するため）

## テーマ選定方針（AI引用を意識する）

2026年時点、Google AI OverviewsやChatGPT検索のようなAI回答エンジンは「〜とは」「使い方」のような一般的な説明系クエリを自前の学習データだけで完結させてしまい、検索結果への遷移（＝サイトへの流入）が起きにくくなっている。この傾向を踏まえ、テーマ・キーワード選定では以下を優先する：

- **避けるべきテーマ**：AIが既存の学習データから合成できてしまう汎用的な説明・ハウツー（「〜とは」「使い方」「学習方法」など、他のどの解説記事にも書けるような一般論）
- **優先すべきテーマ**：AIが学習データに持っていない、または合成できない一次情報
  - 自社の研修・コンサルティング経験から得た独自の知見・意見（例:「Power Apps 内製化が失敗する組織に共通する原因」のような、他では読めない一次情報・独自見解）
  - 具体的な数字・工数・成果を伴う実案件の知見（匿名化は可。ただし**架空の事例を実データのように書かない**。実データが無い場合は一般化されたパターン紹介であることを明示するか、テーマ自体を変える）
  - 独自の用語定義・フレームワークの提示（既存記事の「RAGもどき」のように、独自の切り口で概念を再構成するアプローチ）
- 構成案作成の際、キーワード候補を出す段階で「これはAIが学習データだけで答えられてしまう一般論ではないか」を必ず自問し、該当する場合はより一次情報寄りの角度に絞り込む

## AIO（AI回答エンジン対策）

2026年現在、検索の主戦場はGoogle AI Overviews・ChatGPT検索・Perplexityなどの**AI回答エンジン**に移っている。順位を取ってもクリックされない（ゼロクリック化）ため、記事のゴールは「検索1位を取ること」から「**AIの回答の根拠（ソース）として引用されること**」に変わった。

前章「テーマ選定方針」との関係は次の通り。**テーマ選定＝AIが合成できない一次情報を選ぶ**、**AIO＝その一次情報をAIが引用しやすい形に整形する**。どちらか一方では引用されない。良いネタを持っていても、AIが抜き出せない書き方をすれば拾われない。

法人研修の受注を最優先とする本サイトでは、AI回答に引用されると流入自体は減っても**指名検索とブランド認知が増える**ため、この方向は目的と合致する。

### 1. パッセージ最適化（最重要）

AIは記事を**ページ単位ではなくパッセージ（一節）単位で抜き出す**。したがって「切り出されても単体で意味が通る」ことが引用の条件になる。

- **リードは冒頭100字以内**で、検索意図への直接回答を**断定形**で述べる。前置き・挨拶・背景説明から入らない
- **1見出し1質問**。H3見出しは、それ単体で何に答えるセクションか分かる主題または疑問形にする
- **各セクションの第一段落を50〜140字の回答パッセージにする**。結論を先に置き、理由・詳細は後続の段落に回す
- **パッセージを指示語で始めない**。「これは」「その理由は」「こうした背景から」で始まる段落は、切り出された瞬間に意味を失う。主語・対象を毎回明示する
- **一文は100字以内**を目安にする。長い複文はAIが抽出しにくい

### 2. 検証可能な数値と時点の明示

- AIは**具体的な数字を含む一節**を優先的に引用する。自社の研修現場で実際に得た数値（受講者数、工数削減の実測、よく出る質問の傾向）を積極的に入れる
- **架空の数字を実データのように書かない**。実データが無い場合は、一般化されたパターンであることを明示するか、数値に頼らない切り口にする
- 本文中に「**2026年8月時点**」のように時点を明記する。AIは情報の鮮度を判断材料にする
- 3か月以上更新のない記事はリライト対象とする

### 3. よくある質問（FAQ）セクション

**記事の最後（「まとめ」の後）**に**よくある質問**セクションを置く。「まとめ」より前に置くと、FAQの質問見出しと本文の見出しが入れ子になって構造が壊れる。ここから`app/(main)/blog/[slug]/page.tsx`が`FAQPage`構造化データを自動生成する。

形式は次の2つを受け付ける。**推奨は見出し形式**（記事内の見出しとしても機能するため）。

```markdown
## よくある質問

### Power Automateの承認フローは無料ライセンスでも作れますか？

作れます。Microsoft 365の標準ライセンスに含まれる範囲で承認フローは構築できます。ただし……
```

```markdown
### よくある質問（FAQ）

**Q. Power Automateの承認フローは無料ライセンスでも作れますか？**
A. 作れます。Microsoft 365の標準ライセンスに含まれる範囲で構築できます。ただし……
```

- 見出し形式：「よくある質問」の**下位見出しが質問、その直下の段落が回答**
- Q/A形式：`**Q. 質問**`の**次の行**に`A. 回答`（既存記事`can-non-engineers-code-with-ai`で使われている形式）
- どちらの形式でも、**セクション見出しに「よくある質問」または「FAQ」を含める**こと（これが検出の起点になる）
- 設問は**3〜5問**。回答は1問あたり30〜200字程度で、質問文だけ読んでも成立する独立した回答にする
- 設問は「本文で書ききれなかった周辺の疑問」を拾う。本文の要約を繰り返さない

### 4. 監修者・E-E-A-T

著者の経歴・保有資格・実績の明示は、AI回答での引用率に直接効く。監修者情報は`lib/authors.ts`で一元管理し、記事末尾のプロフィールブロックと構造化データの両方に供給される。

**実在の人物を、本人の許諾なく監修者として掲載してはならない。** 架空の経歴・資格を書くことも当然禁止。監修者データが未設定の記事では、プロフィールブロックも構造化データも出力されない（プレースホルダを出さない）。

### 5. 外部出典の扱い

数値・仕様を引く根拠としてのみ、**公的・一次ソースへの外部リンクを許可**する。許可ドメインは`scripts/lib/blog-lint.mjs`の`ALLOWED_LINK_DOMAINS`で管理している（Microsoft公式ドキュメント、`*.go.jp`等の官公庁、`*.microsoft.com`）。

- 競合メディア・まとめ記事・個人ブログへのリンクは従来通り禁止
- 出典を示すときは、リンクだけでなく**本文中にも出典元の名前と時点を書く**（AIはリンク先を辿らずに本文テキストから判断することがある）

## 自社講座への誘導

**※ 現在は無効です。** 講座6件はすべて`lib/data.ts`のサンプルで、レッスン動画も仮のもの（CLAUDE.md「現状の既知のギャップ」3・4）。この状態で記事から誘導すると、読者を実体のない講座へ送ることになる。**講座の実データと本番動画が入ってから有効化する。**

有効化は`scripts/lib/blog-lint.mjs`の`COURSE_PROMOTION_ENABLED`を`true`にするだけ。それまでは本文に`/courses/`リンクがあるとチェッカーがエラーで止める。

### 何を書くか

法人研修へのCTA（`BusinessBanner`が担当）とは別に、**記事の文脈に合う自社講座を、本文中で柔らかく紹介する**。「読んで理解はしたが、手を動かす段になると動画で手順を追ったほうが早い」と読者が感じる箇所に置くのが自然。

```markdown
画面の操作手順そのものは文章より動画のほうが追いやすい領域です。
[Power Apps はじめの一歩](/courses/powerapps-basic) で一連の流れを扱っています。
```

### ルール

- **1記事1〜2箇所まで。** 3箇所以上は宣伝色が出る（チェッカーが警告）
- **実在する講座にのみリンクする。** 存在しない講座slugはチェッカーがエラーにする（AIがもっともらしい講座名を作ってしまう事故を防ぐ）
- **記事の文脈と関係する講座だけ。** 関連の薄い講座を押し込まない
- **露骨な販売・煽り表現を使わない**（チェッカーがエラーにする）
  - NG: 「今すぐお申し込み」「ぜひご受講ください」「この機会に」「必見です」「お得な」
  - OK: 「〜で扱っています」「手順を追いたい場合は〜が参考になります」「必要であれば〜も用意しています」
- 法人研修への誘導は引き続き**本文に書かない**（`BusinessBanner`と重複する）

## キーワード・カテゴリの扱い

- `category`・`tags`は固定の選択肢ではなく自由記述（コースの`categoryId`のような固定enumはコラムには存在しない）
- 既存カテゴリ例をむやみに増やさず、近い既存カテゴリがあれば揃える（表記ゆれ防止。現状の主な例: 生成AI活用 / DX・内製化）

## 機械チェック

このガイドのルールのうち機械的に判定できるものは、`scripts/lint-blog-draft.mjs`で検査できる。

```
npm run preflight-blog-draft -- "テーマ"      # 書き始める前の事前チェック
npm run lint-blog-draft -- <記事.md>          # 下書き1本を検査
npm run lint-blog-draft                       # content/blog/*.md を一括検査
npm run publish-blog-draft -- <記事.md>       # 検査を通してから microCMS に下書き登録
npm run approve-blog-draft -- <contentId> --yes  # 人が承認して公開
```

**`node scripts/...` を直接実行しないこと。** `node`は`.env.local`を自動で読み込まないため、microCMSの認証情報が渡らず、slug重複チェックがローカル分だけになったり登録に失敗したりする。`npm run`経由なら`--env-file-if-exists=.env.local`が効く。

`npm run publish-blog-draft`はmicroCMSへ登録する直前に同じ検査を実行し、「要修正」が残っていれば登録せずに停止する（`--skip-lint`で無効化可能だが原則使わない）。

「要修正」＝ブランド事故・SEO事故になるもの（旧ブランド名、製品名の表記ゆれ、外部リンク、本文中CTA、slug重複、必須フロントマター欠落、極端に短い本文）。
「確認」＝分量・構成・文体の目安からの逸脱で、意図的なら通してよいもの。

なお、既存記事10本の実測は本文2,440〜7,005字・H3セクション6〜23個であり、上記の目安（2,000〜2,800字／7〜10セクション）より長い記事が多い。チェッカーの閾値はこの実態に合わせて緩めに設定してあり、目安から外れても「確認」止まりで保存はブロックしない。
